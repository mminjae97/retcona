# backend

Follows the code structure from design doc section 6.2 as-is. Each module's responsibility:

| Module | Responsibility | Related design doc section |
|---|---|---|
| `api/` | REST endpoints | All |
| `pipeline/` | extract_claims, context_bundle, 3 judgment modules, merge | Chapter 7 |
| `models/` | DB models (novels, characters, locations ...) | Chapter 4 |
| `ai/` | Embedding · reranker · NLI · LLM client wrappers | Chapter 5 |
| `workers/runner.py` | The job runner: runs the queue's jobs ("run validation", revalidation, a pick's judgment) one at a time in a thread of the API server, which starts it. See "Validation runs" below | Sections 2.2, 10.2 |
| `infra/` | QueueClient (the job queue, a table in the database) · StorageClient · InferenceClient · LLMClient interfaces and implementations | Section 10.4.3 |

## The database

One SQLite file (design doc 10.1): `%LOCALAPPDATA%\Retcona\retcona.db` (elsewhere than Windows, `~/.local/share/retcona/retcona.db`), or the file `DATABASE_URL` names by its full path (`sqlite:///C:/path/to/file.db`). Nothing to install or start: the API server creates it on its first start and, when a new version adds migrations (`db/migrations`), upgrades it before serving anything — copying it to `retcona.before-upgrade.db` beside it first, and in one transaction, so an upgrade that fails changes nothing (`models/db.py`, `upgrade_database`). It won't upgrade while another backend process runs on the same database (an older version left open): close that one first. The runner lock (`infra/queue_client.py`) is a lock on `retcona.db.runner-lock` beside it.

One write transaction at a time: every transaction begins with `BEGIN IMMEDIATE`, taking the database's write lock at once, and another one waits up to 30 seconds for it rather than failing (`models/db.py`). Every foreign key cascades, so deleting a novel deletes everything under it (the trash). Points in time (`created_at`, `updated_at`, `deleted_at`, ...) are kept in UTC (`models/base.py`, `UtcDateTime`); `story_timestamp`, a time in the story, has no time zone.

At startup, after upgrading, the API server checks the database is at the migrations' head. A database at a revision this code doesn't know (a newer version migrated it, and an older one was installed again), or an install without `db/migrations`, is checked against the models instead: it starts, with a warning, if nothing this code needs is missing (`check_database`, `check_schema_is_current`). Without `db/migrations` a new database can't be created at all, so the installer (desktop transition 5/5) has to ship it.

The tests use a database of their own in a temporary folder (`tests/conftest.py`), never the app's.

Logging: the app's own packages (`infra/app_logging.py`) log at uvicorn's `--log-level` (INFO when run without uvicorn), unless a `--log-config` set their level itself. With no logging configured, they print in uvicorn's format through Python's last-resort handler; anything that configures the root logger (a `--log-config`, `logging.basicConfig`, Cloud Logging) takes over completely, with nothing printed twice.

## Validation runs

"Run validation" in the editor (`POST /novels/{id}/episodes/{id}/validations`) records a `validation_runs` row (queued) and, in the same transaction, a job for it on the queue (`jobs`, `infra/queue_client.py`). The API server runs the queue itself: its job runner (`workers/runner.py`, a thread started with the app) loads the models, then takes the jobs one at a time, so nothing has to be started besides `uvicorn` — and only one `uvicorn` process (no `--workers`). An idle runner starts a job as soon as it's committed. The job takes the run (running) and ends it succeeded or failed. The editor polls `GET .../validations/latest` (204 before the first run). While a run is queued or running, another request returns that run instead of starting a second one. Jobs still queued when the app closes run at the next start, and one it closed in the middle of (normally or not) runs again from the beginning (a run writes its results in one transaction at the end, so nothing is half done); one started three times without finishing is given up on. A run still queued or running with no job left for it (given up on, or its job failed in a way it couldn't record) is failed as `abandoned` when it's next read, so it can be run again. How long a job has been running doesn't count — a slow one (on a CPU, or while the PC slept) can't be told from a hung one — so a job that never returns holds up the queue until the app restarts, which runs it again (three starts at most). Only one backend process runs jobs from a database: a second one on the same database (another `uvicorn`) takes the runner lock only once the first is gone, and runs none meanwhile.

What a run does (`pipeline/validate_episode.py`, 7.1):

1. Claim extraction (`pipeline/extract_claims.py`, design doc 7.1.1), with no LLM: the manuscript is split into sentences (dialogue is marked and left out), the characters and places each names are found by their registered names and aliases and by the NER model, the sentences with a cue for a card attribute ("눈동자", "머리카락", "살", ...) are asked for its value by the QA model ("레온의 눈 색깔은?" -> "푸른색"), and a pronoun or dropped subject is linked to the one character the three sentences before it name, if there's exactly one — with two or more, what the pronoun shows (그, 그 사내: `he`; 그녀, 그 소녀: `she`; 그 녀석: nothing) narrows them to the cards narrated with it, and one that's still ambiguous — like a name two characters share — is kept as a pending claim with the characters it could be (`claims.candidates`, `link_status` = `pending`), for the author to pick on the result screen; what they pick is kept per episode (`claim_link_choices`) and applied before judging on the next run, so the sentence isn't asked again (`pipeline/claim_links.py`; the pronoun rules are in `pipeline/extraction_rules.py`). The result screen lists them with `GET /novels/{id}/episodes/{id}/pending-links` and takes the pick with `POST .../pending-links/{claim_id}` (a card among the candidates, or `null` for none of them); a pick is judged right away by the job runner (`judge_linked_claim`, `pipeline/judge_linked_claim.py`: the claim goes `pending` -> `queued` -> `judging` -> a claim like any other, and back to `pending` if the judgment fails or its job is lost). It extracts appearance claims (the fixed attributes: eye and hair color, age, height, scars, origin) and a place's features; behavior and spacetime claims come with the judgments that read them (stages 5 and 4), and the mutable attributes (hairstyle, outfit, ...) once the QA model is evaluated on them. A claim about a registered character carries its ref and the card's name — also when the manuscript uses an alias. Two characters can share a name or an alias but not both: characters with one name need aliases, none shared (409 on the settings screen), and an alias in the text picks the card. A claim with no usable ref is matched by name, then alias (`pipeline/entities.py`); a name that fits more than one character leaves the claim unlinked — not judged, and no new card made for it. A character card also has a gender (male | female | unspecified) and an optional `pronoun` — the one the manuscript narrates it with when that isn't what gender says (`he` 그 | `she` 그녀 | `any`; none follows gender) — set on the settings screen (`api/settings.py`); pronoun linking uses them to tell characters apart when a sentence has only a pronoun (a card with neither set answers to either pronoun, and a lone candidate isn't held to it).
2. Judgment against the setting cards the claims are about (`pipeline/context_bundle.py`, `pipeline/judges.py`, 7.2): a character's fixed attributes (age, eye/hair color, height, scars, origin) and a location's features, by NLI. The card's value, as a sentence, is the premise; the manuscript sentence the claim came from is the hypothesis. A contradiction probability of 0.5 or more is a flag, with that probability as its confidence. Mutable attributes (hairstyle, outfit, ...) aren't judged — they change over the story. Behavior (OOC) and spacetime come in later stages.
3. In one transaction: the episode's earlier claims and flags are replaced; each claim is linked to its character/location by name — an `auto_detected` card is created, with this episode's attributes, for a name the novel doesn't have yet (`pipeline/entities.py`, 7.4) —; and what doesn't contradict anything is added to the settings (`pipeline/merge.py`): a card attribute that's still empty is filled in, and characters' mutable attributes go to `character_state_history` for this episode. An attribute a card already has is never changed by a run. A card remembers which episode each attribute was filled in from (`attr_sources`), so validating that episode again after editing it replaces that value instead of flagging the new wording against the old (or clears it once the sentence it came from is gone from the episode); the author editing the value on the settings screen makes it theirs.

`GET /novels/{id}/episodes/{id}/flags` lists the flags of the episode's latest successful run, most confident first; the result screen (2.4) shows them next to the manuscript. `PATCH .../flags/{id}` acts on one: `accept` (the manuscript is right — its value replaces the card's, which becomes the author's value), `dismiss` (a false positive), `reopen` (undoes a dismissal). A dismissal is recorded apart from the run's flags (`flag_dismissals`, `pipeline/dismissals.py`), so it holds in every later run that flags the same sentence against the same setting — even after a run that didn't flag it. It names the card the flag is about by id (characters can share a name), so renaming a card keeps its dismissals and deleting it deletes them. `GET .../validations/latest` also returns `flag_counts` (open / total flags now).

`POST .../flags/{id}/revalidate` (7.5) judges one open flag again after its setting was supplemented, instead of the whole episode: optionally with `setting`, the card's new value for the flag's attribute (the author's value from then on — the episode's other open flags on that attribute are judged again too). It records a revalidation (`flag_revalidations`) and enqueues a `revalidate_flag` job, which re-runs only that flag's judgment against the card as it is now (`pipeline/revalidate_flag.py`, `pipeline/judges.rejudge`, the same rules as a run). No longer contradicting, the flag becomes `resolved_by_revalidation`, and the revalidation keeps the setting that resolved it; still contradicting, it stays open with the new setting and confidence. Each flag in `GET .../flags` carries its latest revalidation, which the result screen polls while one is queued or running. Not while a run of the episode is in progress (it replaces the flags); a revalidation queued or running with no job pending for it is failed as `abandoned`, as runs are. World-setting rules (free text) don't resolve a flag yet: that needs the judgment LLM.

NLI runs in the API server's process (the job runner) on the CPU (`INFERENCE_BACKEND=cpu`, `infra/inference_client.py`) with the model trained in `ml/nli`: `klue/roberta-base` fine-tuned on KorNLI + KLUE-NLI (chapter 5; how it compares with other checkpoints is in `ml/nli/RESULTS.md`). It's kept on the machine for now, in `ml/nli/runs/mixed` (not committed — train it with `ml/nli`, see its README); `NLI_MODEL` names another local directory or a Hugging Face checkpoint. Without either, the job runner falls back to `Huffon/klue-roberta-base-nli` (downloaded from Hugging Face, about 440 MB), which catches about half as many contradictions in novel prose, and logs a warning. The job runner loads the model at startup and keeps it loaded; if that fails, it still runs jobs, and the first one that needs the model tries again. Expect some false positives (synonyms, sentences that don't state the attribute), which the author dismisses.

Claim extraction (design doc 7.1.1) runs two more models in the same process, through the same `InferenceClient`: the NER model (`ml/ner`, `klue/roberta-base` on KLUE-NER) for names, and the extractive QA model (`ml/qa`, on KLUE-MRC) for attribute values. Like NLI they're kept on the machine that trained them, in `ml/ner/runs/klue` and `ml/qa/runs/klue` (not committed); `NER_MODEL` and `QA_MODEL` name other local directories or Hugging Face checkpoints. There's no public checkpoint to fall back to, so without them claims can't be extracted. The QA model answers "no answer" unless it's about 10 logits more sure of one than of none (`DEFAULT_QA_NULL_MARGIN`, from `ml/qa/RESULTS.md`).

The LLM isn't chosen yet (chapter 5). It's used for OOC judgment only, set in `LLM_MODEL_JUDGMENT` (`infra/llm_client.py`); claim extraction doesn't use one. Until then `LLM_PROVIDER=mock` (`infra/mock_llm.py`) is a stand-in that judges nothing. Failures are recorded on the run as a code: `abandoned`, `episode_missing`, `empty_manuscript`, `inference_failed` (the NLI, NER or QA model couldn't be downloaded, loaded or run), `internal`.

## Trash

Deleting a novel (`DELETE /novels/{id}`) moves it to the trash (`novels.deleted_at`). `GET /novels/trash` lists those, with `purge_after`, 30 days later (`TRASH_KEPT`, `models/novel.py`); `POST /novels/{id}/restore` brings one back until then. The `empty_trash` job (`pipeline/empty_trash.py`) deletes the novels past their 30 days for good, with every row under their `novel_id`, one novel per transaction; the API server queues it right after it starts and then every hour (`api/main.py`) — unless one is still queued or running —, so a novel past its 30 days while the app was closed goes at the next start, and can still be restored until then. A job that finds its novel in the trash — before it starts or by the time it writes — ends without touching its row (`pipeline/in_trash.py`), so after a restore its run or revalidation reads as `abandoned` — to start again — rather than as failed on a missing episode, and a pick goes back to pending.

## Design principles (must follow)

- Every `models/`, `pipeline/` function takes `novel_id` as a required argument (10.1) — blocks isolation gaps at the code level. The one exception is the trash (`pipeline/empty_trash.py`): its pass lists the novels past their days across the app, then deletes each with its own `novel_id` (`_purge`)
- `pipeline/` and `ai/` hold only business logic; queue/storage/inference/LLM access always goes through `infra/` interfaces (10.4.3)
- The 3 judgment modules inside `pipeline/` share the same interface (`claims + context_bundle` in → `flags` out) (6.2)
